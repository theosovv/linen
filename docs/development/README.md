# Spec-driven разработка linen

Этот каталог описывает процесс разработки. Языковые и внешние контракты здесь не дублируются: единственным источником правды является [`SPEC.md`](../../SPEC.md).

## Иерархия документов

1. `SPEC.md` определяет синтаксис, семантику, диагностические коды, CLI, WAV и поэтапный объём работ.
2. `docs/adr/` фиксирует нетривиальные архитектурные решения и их последствия. ADR не заменяет спецификацию.
3. `docs/development/stages/` связывает требования этапа с конкретным объёмом изменений, тестами и результатами проверки.
4. Задача по `task-template.md` задаёт небольшой проверяемый шаг и явный allowlist файлов.
5. Код и тесты реализуют уже записанные решения, а не устанавливают новые контракты.

`AGENTS.md` содержит обязательные рабочие правила для ИИ-агентов. При расхождении краткой документации со `SPEC.md` сначала исправляется документация; спорная семантика не выбирается агентом самостоятельно.

## Цикл работы

1. **Определить текущий этап.** Следующий этап нельзя начинать, пока не выполнен Definition of Done предыдущего. Внутри задачи перечисляются пункты спецификации и нецели.
2. **Проверить полноту контракта.** Если поведение не определено однозначно, работа останавливается и человеку задаётся вопрос. Изменение наблюдаемого поведения сначала согласуется и вносится в `SPEC.md` вместе с changelog.
3. **Зафиксировать архитектуру.** Для нетривиального решения создаётся только относящийся к текущему этапу ADR. Не создаются ADR и модули «на будущее».
4. **Выдать узкую задачу.** В ней указываются разрешённые файлы, запрет production-изменений для тестовых задач, независимые oracles и команды проверки. Шаблон: [`task-template.md`](task-template.md).
5. **Реализовать минимальный diff.** Существующие контракты и тесты не ослабляются. Найденные побочные идеи переносятся в отдельную задачу, а не реализуются попутно.
6. **Проверить результат.** Сначала запускаются релевантные тесты, затем `cargo fmt --check`, `cargo clippy --all-targets --locked -- -D warnings`, `cargo test --all-targets --locked`, `cargo test --doc --locked` и rustdoc с предупреждениями как ошибками.
7. **Записать фактический результат.** В документе этапа отмечаются выполненные команды, найденные дефекты и ограничения. Незапущенная проверка не считается пройденной.
8. **Завершить этап.** Все пункты DoD из `SPEC.md` и release checklist должны быть выполнены. Статус этапа меняется на `завершён` только после этого.

## Правила изменения контрактов

- Новая возможность начинается с изменения спецификации человеком или с его явного поручения.
- Каждый сознательный контрактный break получает запись в `SPEC.md` и корневом `CHANGELOG.md`.
- Старые compatibility fixtures не переписываются под новое поведение без такого изменения.
- Каждый исправленный дефект получает минимальный regression test с независимым expected.
- Рефакторинг без смены поведения не требует новой семантики, но требует полного набора проверок.

## Работа с ИИ-агентами

По умолчанию агент работает в режиме read-only для production-кода и может менять только `tests/`, `fixtures/` и непосредственно необходимый test-support. Любое другое изменение требует явного allowlist в задаче.

Основной lexer/parser, type checker, IR, VM, DSP и оптимизации пишет человек. Агенту делегируются тесты, генераторы, ревью и разрешённый спецификацией бойлерплейт. Подробные ограничения находятся в `SPEC.md`, раздел 8, и в `AGENTS.md`.
