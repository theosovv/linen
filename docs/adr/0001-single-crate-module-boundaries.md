# 0001. Один crate и границы модулей

- Статус: принят.
- Дата: 2026-11-11.

## Контекст

На этапе 0 нужна устойчивая структура без инфраструктуры, опережающей реальную функциональность. `SPEC.md` требует один crate, library facade и тонкий CLI entry point. Будущие стадии компилятора пока не существуют.

## Варианты

1. Workspace из отдельных crates для frontend, VM и DSP. Даёт изоляцию, но создаёт преждевременные границы и сборочную сложность.
2. Один package с library и binary, где модули появляются только вместе с реальной ответственностью. Соответствует текущему объёму и сохраняет возможность позднего разделения.
3. Только binary. Затрудняет независимые библиотечные тесты diagnostics и противоречит требуемому facade.

## Решение

Используется второй вариант. `src/lib.rs` экспортирует только реально существующий публичный API, `src/main.rs` содержит только инфраструктурный CLI. На этапе 0 существует модуль `diagnostic`; каталоги `syntax`, `sema`, `ir`, `bytecode`, `vm`, `dsp` и `render` не создаются.

Файл `api.rs` также откладывается: до появления стадий компиляции ему нечего компоновать без заглушек. Корень library crate выполняет роль текущего facade. Направление зависимостей следующих модулей определяется `SPEC.md` §5.4.

## Последствия

- Diagnostics можно тестировать через library API без запуска процесса.
- Пустые trait-ы и универсальные wrappers не закрепляют преждевременный дизайн.
- Добавление нового модуля должно сопровождаться реальной функциональностью и соблюдением направленных зависимостей.
- Разделение на workspace потребует отдельного обоснования и нового ADR.

## Проверка

- Integration tests используют crate `linen` как библиотеку.
- Binary tests проверяют только аргументы, streams и exit codes.
- CI выполняет fmt, clippy, все тесты и сборку документации для одного package.
