# 0003. Float, явный lift и граница наивного интерпретатора

- Статус: принят.
- Дата: 2026-11-16.
- Дополняет: ADR 0001, 0002 и 0012.

## Контекст

Этап 2 должен дать первый путь `source → Typed AST → naive sample interpreter → WAV`, не реализуя IR, bytecode и VM из этапа 3. `Float` вычисляется как `f64` на этапе построения программы, а `Sig` содержит runtime-значения `f32`. Неявные преобразования нельзя восстанавливать интерпретатором по догадке, а resolved definitions должны сохранять identity и `SourceSpan`.

До уточнения спецификация одновременно требовала `FunctionId` и nested-scope tests на этапе 2, хотя пользовательские функции и блоки появляются только на этапе 4. Также не был определён код для нечислового `Float` или значения, которое нельзя представить конечным `f32`.

## Варианты

1. Оставить преобразования неявными и выполнять их в интерпретаторе. Это меньше узлов, но скрывает семантику и усложняет последующий lowering.
2. Добавить отдельный Typed AST с типами, resolved IDs, spans и явным `LiftFloatToSig`. Это соответствует общему pipeline и делает границу перед IR проверяемой.
3. Использовать строки как identity до появления IR. Это закрепило бы глобальный namespace и потребовало бы повторной миграции.
4. Реализовать FunctionId и nested scopes до появления соответствующего синтаксиса. Это создало бы internal-only функциональность без пользовательского контракта.
5. Сразу строить IR. Это нарушило бы последовательность этапов и объём Beep.

## Решение

Выбраны варианты 2 и отказ от преждевременных FunctionId/scopes/IR.

### Типы и lift

- `Float` использует `f64` во frontend и compile-time арифметике; `Sig` использует `f32` на каждом семпле.
- Числовой литерал и compile-time операция обязаны давать конечный `f64`. Нарушение — `E2105` с primary span соответствующего литерала, unary или binary expression.
- Конечный `f64` может временно превышать диапазон `f32` во время compile-time арифметики. При каждом `Float → Sig` lift выполняется checked conversion: если результат `as f32` бесконечен, возвращается `E2105` с primary span исходного lifted expression. Обычное IEEE-округление, включая underflow к нулю, не считается overflow.
- `LiftFloatToSig` вставляется type checker в аргументы, смешанную арифметику, аннотированные `Sig` bindings и `out`. Обратное преобразование запрещено.
- Compile-time деление на ноль диагностируется раньше общей проверки конечности как `E2104`. Динамическое деление следует IEEE 754; нечисловой выход обнаруживается как `E4001`.

### Identity и Typed AST

- `BindingId` — детерминированный индекс top-level declaration в одной компиляции. `BuiltinId` — индекс статического builtin descriptor. Повторное использование definition сохраняет ID.
- На этапе 2 существует один плоский scope. `FunctionId`, пользовательские функции, nested scopes, shadowing и связанные identity tests относятся к этапу 4.
- Typed AST отделён от syntax AST. Каждый binding, expression и render сохраняет `SourceSpan`; идентификаторы остаются доступны для diagnostics, но не служат resolved identity.
- `CompileSession` явно владеет `SymbolStorage`. Source-level compile outcome сохраняет `SourceMap` и storage вместе с результатом.

### Наивный execution path

- `check` сохраняет текущий syntax AST в успешном результате, но дополнительно выполняет name/type/duration checks с sample rate по умолчанию 48 000 Гц.
- `compile` получает явный `RenderConfig`, проверяет его и возвращает Typed AST и вычисленный sample count. `max_output_seconds` применяется только перед рендером, а не как языковое ограничение `check`.
- Наивный интерпретатор находится в `src/render/interpreter.rs` как временная production-реализация короткого пути этапа 2. Он исполняет Typed AST по одному семплу, не создаёт IR/bytecode/VM и не выполняет host I/O.
- Числовой алгоритм осциллятора находится в `dsp`; WAV и цикл записи — в `render`. После parity на этапе 3 production-интерпретатор заменяется VM, а независимый test-support reference остаётся oracle.

## Последствия

- Все lifts видны в Typed AST и тестируются без анализа приватного состояния интерпретатора.
- Проверка конечности `f64` и проверка диапазона при lift — разные операции; большой, но конечный промежуточный `f64` не отклоняется автоматически.
- Плоский scope не создаёт infrastructure для будущих модулей или функций. Их контракты не реализуются досрочно.
- Временное расположение production-интерпретатора не разрешает переносить DSP-формулы в WAV или CLI.
- `E2105` получает самостоятельный стабильный смысл; существующие коды не переиспользуются.

## Проверка

- Typed AST tests проверяют `BindingId`, `BuiltinId`, тип каждого expression, все lifts и `SourceSpan`.
- Boundary cases различают infinite `f64`, конечный `f64`, который переполняет `f32`, и допустимое округление/underflow.
- Resolution tests проверяют declarations в порядке исходника, unknown/forward/self references, duplicate names и повторное использование ID.
- Numerical tests используют аналитические формулы и независимый test-support reference, а production evaluation не вычисляет собственные expected.
- Этап 3 должен доказать parity перед удалением production-интерпретатора; block VM этим ADR не вводится.
