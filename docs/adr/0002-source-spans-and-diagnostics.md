# 0002. Source spans и структура diagnostics

- Статус: принят; решение о span без source identity заменено ADR 0012.
- Дата: 2026-11-11.

> Ниже сохранено историческое решение этапа 0. Структура `Diagnostic`, severity и стабильные коды остаются в силе. На этапе 1A `Span` заменяется на `SourceSpan` с `SourceId`, а source rendering разрешает источник через `SourceMap`; точные правила находятся в ADR 0012 и `SPEC.md` 0.2.0.

## Контекст

Этап 0 должен предоставить базовые diagnostics, пригодные для lexer/parser следующего этапа и для тестов без CLI. `SPEC.md` задаёт полуинтервальные byte spans, severity, стабильные коды, primary/secondary spans и notes.

## Варианты

1. Свободные строки ошибок и offsets без общей структуры. Просто, но не поддерживает стабильные assertions и source rendering.
2. Структурированные `Span` и `Diagnostic` с проверкой инварианта диапазона и enum начальных кодов. Даёт явные контракты без привязки к parser.
3. Полный source renderer на этапе 0. Потребовал бы заранее решить правила Unicode/CRLF и оформление вывода, не нужные текущему этапу.

## Решение

Выбран второй вариант:

- `Span` хранит `usize` offsets `[start, end)`; публичный конструктор возвращает ошибку при `start > end`, а пустой диапазон допустим.
- `DiagnosticLabel` связывает span с пояснением.
- `Diagnostic` хранит severity, `ErrorCode`, основное сообщение, один primary label, списки secondary labels и notes.
- `ErrorCode` — enum начальных ситуаций из `SPEC.md` §6.2; строковое представление соответствует стабильному коду `E####`.
- Типы не зависят от syntax, CLI, файловой системы или I/O.
- Source rendering и вычисление line/column откладываются до этапа, которому они нужны. Правила отображения не фиксируются этим ADR.

Rust API внутренних структур не объявляется стабильным; стабильны введённые диагностические коды и их смысл.

## Последствия

- Тесты могут проверять код, offsets, labels и notes напрямую.
- Некорректный диапазон обнаруживается при создании, без panic на пользовательском вводе.
- Добавление новых кодов расширяет enum, но смысл существующих кодов нельзя переиспользовать.
- Будущий renderer оформляется отдельно и не меняет хранимые byte offsets.

## Проверка

- Unit-level integration tests проверяют границы spans и полный состав diagnostic.
- Отдельный тест сравнивает весь набор кодов с явной таблицей и проверяет уникальность.
- Ни один тест diagnostics не запускает binary.
