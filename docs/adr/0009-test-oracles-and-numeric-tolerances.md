# 0009. Независимые test oracles и числовые допуски

- Статус: принят.
- Дата: 2026-11-16.

## Контекст

Этап 2 добавляет первые числовые результаты и бинарный аудиоформат. Expected нельзя получать проверяемой production-функцией: одинаковая ошибка в алгоритме и expected сделала бы тест тавтологическим. При этом точный WAV hash и битовая идентичность `sin` на разных платформах не являются переносимым контрактом.

## Варианты

1. Сравнивать production с его собственным повторным запуском. Это проверяет детерминизм, но не правильность.
2. Использовать аналитические семплы, вручную рассчитанные WAV bytes и независимый reference interpreter. Это разделяет проверку формулы, state machine и внешнего формата.
3. Использовать только RMS или golden WAV hashes. RMS не различает многие разные сигналы, а hash чувствителен к платформенным различиям transcendental functions.

## Решение

Выбран второй вариант.

### Иерархия oracles

- Основные sine tests используют явные индексы и аналитические значения из спецификации. Для остальных samples допускается независимо записанная формула с явно вычисленным начальным состоянием.
- `test-support/reference/` содержит отдельный посемпловый interpreter Typed AST для поддерживаемого Beep-подмножества. Он не вызывает production interpreter, production DSP, WAV-writer, bytecode или VM и не разделяет их state transitions.
- Reference проверяется самими аналитическими vectors. Совпадение production и reference без аналитического случая не считается достаточным доказательством формулы.
- WAV header, chunk sizes и quantization vectors рассчитываются вручную и записываются как независимые byte arrays. Counts, enum, `SourceSpan`, PCM bytes и error sample index сравниваются точно.

### Допуски

Для обычного `f32` audio:

```text
abs(actual - expected) <= abs_tol + rel_tol × abs(expected)
abs_tol = 2e-5
rel_tol = 2e-5
```

- Сравнение посемпловое; failure сообщает первый различающийся индекс.
- Compile-time `f64` arithmetic сравнивается с независимым `f64` выражением и точными векторами там, где результат представим точно. Для неассоциативных перестановок общий допуск не вводится.
- Reset требует повторения последовательности в пределах того же допуска; чистая арифметика и PCM bytes сравниваются точно.
- Допуск нельзя увеличивать ради зелёного CI. Фильтры и специальные алгоритмы будущих этапов получают отдельное обоснование.

### Покрытие

- Positive, negative и boundary cases обязательны для types, durations, config, runtime errors и WAV.
- Diagnostics проверяют код, `SourceId`, primary byte span и, для `E4001`, структурированный `sample_index`.
- Повторная компиляция/рендер проверяется в одном process и через независимые CLI processes. Physical path не входит в semantic artifacts.
- Обычные tests не используют сеть, системное время, внешние аудиофайлы или нефиксированный random.

## Последствия

- Reference не заменяет аналитические tests и не является production API.
- При расширении языка reference поддерживает только явно добавленное подмножество; unsupported input не превращается молча в ноль или тишину.
- Изменение production DSP требует пересмотра независимых expected и changelog при изменении render compatibility.
- Этап 3 добавляет differential corpus и block partitions, не ослабляя исходные аналитические assertions.

## Проверка

- Сам reference проходит фиксированные sine/gain vectors до использования как oracle.
- WAV tests содержат полный ожидаемый 44-byte header для известного sample count и явные little-endian PCM16 vectors.
- Review каждого нового test подтверждает пункт спецификации и независимость expected от проверяемой функции.
