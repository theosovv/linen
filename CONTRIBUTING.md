# Участие в разработке linen

Проект исследовательский: важна не скорость добавления возможностей, а понятная семантика, ручная реализация ядра и независимая проверка поведения.

## Основные правила

1. Прочитайте `SPEC.md`, документ текущего этапа и относящиеся ADR до изменения кода. Для compiler architecture дополнительно прочитайте [`docs/linen — подготовка к экосистеме.md`](docs/linen%20%E2%80%94%20%D0%BF%D0%BE%D0%B4%D0%B3%D0%BE%D1%82%D0%BE%D0%B2%D0%BA%D0%B0%20%D0%BA%20%D1%8D%D0%BA%D0%BE%D1%81%D0%B8%D1%81%D1%82%D0%B5%D0%BC%D0%B5.md).
2. Не начинайте следующий этап до выполнения DoD предыдущего. Корректирующий этап 1A завершён и принят; следующий этап 2 начинается по отдельной явной задаче.
3. Изменение синтаксиса, типов, diagnostics, CLI, WAV или DSP сначала согласуется как изменение спецификации.
4. Нетривиальные архитектурные решения оформляются через ADR.
5. Не добавляйте зависимости, toolchain updates и модули для будущих этапов без явной задачи.
6. README и упрощённая документация не должны обещать несуществующую функциональность.
7. Source libraries, packages, registry и device artifacts — разные будущие артефакты. Не реализуйте их CLI, manifest, loader или plugin infrastructure под видом текущей подготовки.

Полный процесс описан в [`docs/development/README.md`](docs/development/README.md).

## Человек и ИИ-агенты

Человек принимает решения о языке и архитектуре и пишет основной production-код компилятора, VM и DSP. Агентам делегируются:

- unit-, integration-, numerical-, property- и regression-тесты;
- fixtures, fuzz generators и независимые test oracles;
- multi-source и deterministic compilation tests;
- read-only ревью скрытого I/O, глобального состояния и зависимостей модулей;
- разрешённый CLI/CI и механический бойлерплейт;
- документация по уже принятой спецификации.

Каждая агентская задача должна содержать allowlist файлов. Без него агент может менять только тесты и необходимый test-support. Используйте [`docs/development/task-template.md`](docs/development/task-template.md) и правила [`AGENTS.md`](AGENTS.md).

## Подготовка окружения

Установите `rustup`, затем из корня репозитория:

```bash
rustup show
cargo build --locked
```

`rust-toolchain.toml` выбирает нужную версию Rust и компоненты автоматически. `Cargo.lock` должен оставаться в репозитории.

## Тесты и независимые oracles

- Проверка должна относиться к конкретному пункту спецификации.
- Не вычисляйте expected той же production-функцией, которую проверяете.
- Для diagnostics проверяйте код, `SourceId` и primary byte span.
- Используйте synthetic in-memory sources для multi-source tests; не смешивайте логическое имя с физическим путём. `SourceId` применяйте только с создавшей его `SourceMap` или её идентичной копией: независимые карты могут выдавать одинаковые индексы.
- Проверяйте повторную компиляцию в одном и разных processes там, где затронут порядок diagnostics или semantic artifacts.
- Для WAV используйте независимо рассчитанные bytes.
- Для DSP используйте аналитические векторы или независимый reference и посемпловое сравнение.
- Не удаляйте и не ослабляйте падающие проверки, не добавляйте `#[ignore]`, не увеличивайте допуски ради зелёного CI.
- Каждый bug получает минимальный reproducer и постоянный regression test.

Если новая проверка выявила дефект ядра в задаче «только тесты», зафиксируйте reproducer и сообщите о нём; production-исправление требует отдельного разрешения.

## Перед pull request

Запустите:

```bash
cargo fmt --check
cargo clippy --all-targets --locked -- -D warnings
cargo test --all-targets --locked
cargo test --doc --locked
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --locked
```

В pull request укажите затронутые пункты спецификации и ADR, allowlist агентских изменений, выполненные команды и оставшиеся ограничения. Для compiler changes отдельно отметьте сохранение `SourceSpan`, отсутствие скрытого I/O и влияние на детерминизм. Не смешивайте независимые возможности и рефакторинг в одном изменении.

## Документация

Основная документация пишется на русском; идентификаторы и API — на английском. Изменили фактическое поведение — обновите относящиеся документы. Изменили устойчивый контракт — сначала согласуйте спецификацию и добавьте записи в её changelog и корневой `CHANGELOG.md`.

Если новое требование затрагивает уже завершённый этап, не переписывайте его исторический отчёт так, будто требование выполнялось изначально. Добавьте корректирующий stage document с текущим пробелом, миграцией, compatibility tests и отдельным DoD. Пример: [`stage-01a-ecosystem-foundation.md`](docs/development/stages/stage-01a-ecosystem-foundation.md).
