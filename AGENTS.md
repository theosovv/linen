# Руководство для ИИ-агентов

Этот файл задаёт рабочие правила репозитория. Он не расширяет полномочия агента сверх явной задачи пользователя.

## Перед началом

1. Прочитайте [`SPEC.md`](SPEC.md) — единственный источник правды для синтаксиса, семантики и внешних контрактов.
2. Изучите [`docs/development/README.md`](docs/development/README.md), документ текущего этапа и относящиеся к задаче ADR.
3. Повторите требования задачи: объём, allowlist файлов, нецели, критерии приёмки и команды проверки.
4. Проверьте фактическое состояние файлов и тестов, не полагаясь только на документы или предыдущий отчёт.

Документация и идентификаторы в коде пишутся на русском и английском соответственно. Сообщения пользователю — на языке пользователя.

## Текущее состояние

- Этап 1 завершён. Следующий производственный этап — type checker, наивный интерпретатор и WAV из этапа 2.
- Реализованы diagnostics, tokens/AST, lexer, parser, parser limits, Unicode/CRLF locations, source renderer и команда `check`.
- `run`, `inspect`, type checker, audio и VM ещё не реализованы.
- Не начинайте следующий этап без явной задачи и выполненного DoD предыдущего.

## Полномочия и границы изменений

Если задача не содержит allowlist, действует режим **read-only + тесты**: разрешено менять только `tests/`, `fixtures/` и непосредственно необходимый test-support. Для read-only ревью не меняйте ничего.

Если для выполнения задачи нужны другие файлы, остановитесь и запросите расширение allowlist. Явная задача на production-изменение должна перечислять разрешённые файлы или каталоги.

По умолчанию запрещено:

- менять `SPEC.md`, ADR, публичный API или CLI без явного поручения;
- реализовывать production-функциональность, чтобы тест прошёл, если задача была только на тесты;
- добавлять зависимости или повышать toolchain;
- рефакторить соседние модули или форматировать весь репозиторий ради локального изменения;
- удалять, ослаблять, пропускать тесты или добавлять `#[ignore]`;
- увеличивать числовые допуски или массово обновлять snapshots без отдельного обоснования;
- создавать placeholders для будущих этапов, `todo!()`, `unimplemented!()` и достижимые пользователем `unreachable!()`;
- делать commit, branch, push или публиковать пакет без явной пользовательской задачи.

Человек пишет основной lexer/parser, type checker, IR, VM, DSP и оптимизации. Агенты преимущественно готовят тесты, fixtures, генераторы, ревью и разрешённый спецификацией бойлерплейт. Полное разделение работ описано в `SPEC.md` §8.

## Spec-driven процесс

1. Сначала сверьте задачу с текущим этапом и пунктами спецификации.
2. При неоднозначной или противоречивой семантике остановитесь и задайте вопрос. Не выбирайте поведение самостоятельно.
3. Наблюдаемое изменение сначала согласуется и попадает в `SPEC.md`; сознательный контрактный break также получает changelog entry.
4. Нетривиальное архитектурное решение фиксируется в отдельном ADR до реализации.
5. Используйте [`docs/development/task-template.md`](docs/development/task-template.md) для новых агентских задач.
6. Не реализуйте будущие возможности попутно; вынесите их в отдельную задачу.

`docs/SPEC.md` не создавайте: копии спецификации расходятся. Актуальный файл находится только в корне.

## Архитектура и стиль Rust

- Один package с library и binary; новый workspace или crate требует обоснования и ADR.
- `src/lib.rs` — небольшой facade только для реально существующего API.
- `src/main.rs` — аргументы, streams, exit codes и файлы; логика компилятора там не размещается.
- `src/diagnostic.rs` не зависит от parser, VM или CLI.
- Новые модули появляются вместе с реальной функциональностью и соблюдают направление зависимостей `SPEC.md` §5.4.
- Не используйте глобальные mutable singletons, скрытые fallback и неявный I/O в библиотеке.
- Сохраняйте существующий стиль, не добавляйте шумные комментарии и не оставляйте dead code.
- `unsafe` запрещён настройкой crate. Toolchain зафиксирован в `rust-toolchain.toml`; `Cargo.lock` коммитится.

## Требования к тестам

- Каждый тест ссылается на конкретное требование спецификации в задаче или названии проверки.
- Expected задаётся явно, аналитической формулой или независимым reference, но не проверяемой production-функцией.
- Проверяйте positive, negative и boundary cases.
- Для diagnostics проверяйте код и primary span, а не только наличие ошибки.
- Для DSP используйте посемпловые сравнения и формулу `abs(actual - expected) <= abs_tol + rel_tol * abs(expected)` из спецификации.
- Не используйте сеть, текущее время, нефиксированный random или внешние аудиофайлы в обычных тестах.
- Каждый исправленный bug получает минимальный regression fixture и тест, который падает на старой версии.
- Если тест выявил production-дефект при задаче «только тесты», оставьте минимальный падающий regression test и сообщите о дефекте, не исправляя ядро.

## Проверки

После узких релевантных тестов запустите общий набор:

```bash
cargo fmt --check
cargo clippy --all-targets --locked -- -D warnings
cargo test --all-targets --locked
cargo test --doc --locked
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --locked
```

CI должен воспроизводить эти проверки. По мере появления соответствующих suites добавляются `compatibility`, `differential` и `properties`; несуществующие targets не вызываются заранее.

## Definition of Done и отчёт

- Diff ограничен разрешёнными файлами и текущим этапом.
- Нет placeholders, новых ignored/flaky/network-dependent тестов и скрытых fallback.
- Релевантные и общие проверки действительно запущены и прошли.
- README и документация описывают только фактически работающие возможности.
- Новые созданные проверками артефакты удалены, если они не нужны репозиторию.
- В финальном отчёте перечислены изменения, команды с результатами, найденные дефекты и оставшиеся ограничения. Непроверенное явно названо непроверенным.
